# 合规性设计：短信验证码与客服入口

## 结论

本 App 需要落实两条中国大陆合规设计：一是短信验证码界面写明验证码短信的实际发送方抬头，二是提供打开 App 后最多两步可达的"帮助与客服"入口。两者都不改变产品连接模式，只在 UI 层补齐责任边界，避免用户混淆、避免将来被网信办检查时先被要求整改。

## 短信验证码：发送方抬头与 App 名称不一致

### 问题

短信验证码（OTP）本身是安全的。这里存在一种风险：用户短信列表里有很多条验证码，用户看错了，把另一条的验证码输了进来。这本来完全是用户自己的责任。

但中国大陆的短信签名合规要求带来一个现实问题：涉及短信验证码的应用，基本只能申请到企业名称抬头的短信签名，很难直接申请到 App 名称作为抬头——除非用 App 名称额外注册了商标。因此短信抬头与 App 名称天然不一致：用户对着列表里的多条验证码，无法分辨哪一条才是本 App 发的。

### 设计

在 App 内发送短信验证码的界面上写明发送方抬头：

> 发送验证码，请输入来自杭州绳匠科技有限公司的短信验证码。

这样用户知道应该在短信列表里找哪一条；同时也把输错验证码的责任边界在界面上写清楚了。从功利的角度说，这一步只是把责任从我们头上转移到用户头上，但它是合规审查中可见的、可解释的动作。

### 落地位置

- `AccountActivity` 的短信验证码登录界面：验证码输入框下方显示上述提示。
- `AccountActivity` 的安全验证对话框（改密码、关两步验证、退款、注销等场景选短信验证码时）：验证码输入框下方显示同样提示。
- 提示必须与后端实际使用的短信签名保持一致；后端更换签名主体时，界面文案必须同步更新。

## 联系客服：两步可达的入口

### 问题

大厂 App 总是在打开后最多两步的地方提供一个联系客服的入口，国家网信办近期确实在查这一点。虽然本 App 不是大厂 App，也应做到同等责任——即便将来被查，也不至于成为先被整改、再被放走的那一批。

最常见的模式是：打开 App 进入关于页面，或点开侧边栏菜单，页面下方有一个联系客服按钮（小红书就是这么做的）。

### 设计

在"我的 / 关于 / 设置 / 菜单"类页面中提供"帮助与客服"按钮：

- 图标使用经典的头戴式带麦克风客服耳机图标。
- 点击跳转到客服页面。

客服页面即现有 `ContactDeveloperActivity`，内容为：

- 一键加群：跳转 QQ 加群（`https://qm.qq.com/q/cJNTQuxfoW`，群号 `1083518433`）；未安装 QQ 时回退到浏览器打开。
- 复制群号。
- 复制加群链接。
- QQ 群二维码。

### 落地位置

- "我的"页（`ProfileActivity` 的 `ProfileNavigation`）提供"帮助与客服"入口，图标为 `Icons.Default.SupportAgent`（头戴式带麦克风客服耳机），点击跳转 `ContactDeveloperActivity`。从打开 App 到首页点"我的"再进入客服页，共两步。
- `ContactDeveloperActivity`（`ContactDeveloperScreen`）即客服页面：一键加群（跳转 QQ，未安装 QQ 时回退浏览器）、复制群号、复制加群链接、QQ 群二维码。
- `MainActivity` 的"联系客服"按钮继续保留在未授权 / 授权校验失败等门禁状态下，保证登录前、授权失败等异常路径也能联系客服。

## 维护规则

- 短信验证码界面的发送方抬头文案必须与后端短信签名主体一致，改签名必须改文案。
- 客服入口不允许从设置 / 关于 / 菜单类页面移除；入口文案与图标使用"帮助与客服"+ 头戴式客服耳机图标。
- 客服页的 QQ 群号、加群链接与二维码集中维护，不得出现群号与链接指向不同群的复制项。
