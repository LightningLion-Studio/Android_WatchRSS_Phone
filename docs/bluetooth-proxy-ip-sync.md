# 蓝牙桥接网络上的 IP 同步约束

## 结论

手机与 OPPO Android 手表配对后，手表可以通过系统提供的蓝牙网络代理访问手机的 IPv4 地址。这里的“蓝牙同步后走 IP”并不是让用户配置 Wi-Fi，也不是新增一种连接模式：RFCOMM 仍负责发现、认证和传递短小的端点描述，随后大数据通过同一配对关系建立的 IP 链路和 WebSocket 传输。

在当前 OPPO 手表系统代理中，TCP 目标端口存在一个关键限制：**端口必须位于 `1..32767`**。不要把同步服务改回 `NanoWSD(0)` 或其他随机临时端口，因为 Android 通常会分配大于等于 32768 的端口，手表侧看似建立连接，实际请求却到不了手机。

因此手机同步服务固定尝试 `30000..30015`，并把实际成功监听的端口放进 RFCOMM 端点描述。`18765` 保留给 Watch S 视频播放器的本地音频探测服务，不与同步服务复用。

## 现场证据（2026-08-09）

测试设备：

- 手机：Samsung SM-F9560，Wi-Fi 地址 `192.168.77.81`
- 手表：OPPO OWW242，Android 11
- 手表经蓝牙代理访问手机时，手机看到的对端地址为 `10.30.169.9`

从手表应用 UID 发起到手机的 HTTP 请求，结果如下：

| 手机监听端口 | 结果 |
|---:|---|
| `18765` | HTTP 200，手机收到请求 |
| `30000` | HTTP 200，手机收到请求 |
| `32767` | HTTP 200，手机收到请求 |
| `32768` | 超时，手机未收到请求 |
| `37730` | 超时，手机未收到请求 |
| `40000` | 超时，手机未收到请求 |

这证明 `192.168.77.81` 本身是可达的，故障点不是私网地址或路由，而是端口跨过了有符号 16 位边界。

手表系统组件的反编译结果也与实测一致：`HeytapNatSession.remotePort` 使用 Java `short` 保存目标端口，`TCPTunnel` 建立上游连接时直接把它传给连接构造器，没有先执行 `remotePort & 0xffff`。日志路径做了无符号掩码，因此日志里显示的端口可能正常，实际连接参数仍是负数。

## 为什么 Watch S 视频播放器的音频服务可用

Watch S 视频播放链路已经采用同一思路：手机端 `LocalAudioProbeServer` 在固定端口 `18765` 启动 HTTP 服务，通过蓝牙控制消息把音频 URL 交给手表，手表播放器再请求该 URL。`18765 < 32768`，所以没有触发上述代理缺陷。

这也说明“蓝牙桥接后访问手机 IP”是可行的；此前同步失败是随机服务端口越界，并非该链路不存在。

## 同步链路

1. 手表开启短时 RFCOMM 服务，手机连接已配对设备。
2. 手机通过 RFCOMM 返回带 HMAC 的 IP 端点描述，其中包含监听地址、端口和认证信息。
3. 手表通过蓝牙代理网络连接手机 WebSocket，并发送 `HELLO` 完成认证。
4. 游标、清单、文章和阅读资源经 WebSocket 传输；RFCOMM 仍作为引导和回退通道。

WebSocket 读取超时设置为 10 分钟。同步阶段可能在生成清单或处理数据库时停顿数秒，NanoWSD 默认约 5 秒的读取超时会把健康连接误判为断开。

IP 响应写入后的确认等待同样是 10 分钟。`WebSocket.send()` 只表示数据进入 OkHttp
队列；蓝牙代理可能需要近一分钟才把数 MB 响应排空，RFCOMM 使用的 10 秒确认窗口会在
手机仍读取最后一帧时误关连接。

每次用户手动同步都先通过 RFCOMM 重新探测并取得新端点，不复用上次留下的 WebSocket。
OPPO 手表回收后台路由后，手机侧旧 WebSocket 仍可能短暂显示为 open，直接复用会卡在游标阶段。

## 可选的熄屏媒体保活

部分 OPPO 手表固件会在熄屏后约 5 秒强停普通后台应用。高级设置里的“同步媒体保活”默认
关闭；开启后也不会让应用每时每刻常驻。它在 RFCOMM 客户端已经连接、同步实际开始时播放
全零 PCM 静音音轨，并通过会话租约跨过 RFCOMM 到 IP 的切换及各同步阶段之间的短暂间隔，
整次同步空闲 30 秒后释放音轨。这样用户在同步过程中熄屏时，媒体策略可继续保护传输。

该机制不用于从已经熄屏且应用已被系统强停的状态唤醒同步；需要先在手表亮屏、应用存活时
建立连接，再熄屏验证保活。

## 维护规则

- `IP_SYNC_PORT_CANDIDATES` 的每一个值都必须处于 `1..Short.MAX_VALUE`。
- 不要使用端口 `0` 让内核随机分配同步端口。
- 不要占用 Watch S 音频服务的 `18765`。
- 修改端口范围或读取超时后，必须运行 `IpSyncProtocolTest`。
- 真机验证至少要覆盖 `/health`、WebSocket `HELLO`、清单传输和最终数据收敛；仅看到 socket connected 不算成功。
